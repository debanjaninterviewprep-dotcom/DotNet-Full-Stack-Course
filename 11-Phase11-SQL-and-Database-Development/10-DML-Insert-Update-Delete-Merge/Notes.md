# Topic 10: DML — INSERT, UPDATE, DELETE & MERGE

> Every write TaskFlow makes — a new task, a status change, a bulk import from a spreadsheet, a nightly purge of cancelled tasks older than a year — goes through exactly four statements. Getting `SELECT` wrong shows you a bad report. Getting DML wrong **destroys or corrupts data**, in a transaction that other sessions may already be reading. This topic covers all four statements, the `OUTPUT` clause that turns any of them into an audit trail, `MERGE` and the well-documented reasons many teams avoid it, and the batching/locking discipline that separates a safe production script from an incident.

---

## 1. `INSERT` — Every Form

```sql
USE TaskFlowDb;
GO

-- Single row, explicit column list. ALWAYS list columns -- never rely on position.
INSERT INTO app.Labels (LabelName, ColorHex)
VALUES (N'blocked-external', '#8B0000');

-- Multi-row VALUES constructor -- one INSERT, one statement, one log record.
INSERT INTO app.Labels (LabelName, ColorHex)
VALUES (N'needs-design', '#C2185B'),
       (N'customer-reported', '#F57C00');

-- INSERT ... SELECT -- copy/derive rows from another query.
INSERT INTO app.TaskLabels (TaskId, LabelId)
SELECT t.TaskId, (SELECT LabelId FROM app.Labels WHERE LabelName = N'needs-design')
FROM app.Tasks AS t
WHERE t.ProjectId = 8 AND t.StatusId NOT IN (6, 7);
```

> **Anti-pattern:** `INSERT INTO app.Labels VALUES (N'x', '#000000')` with no column list. It compiles today and silently inserts into the wrong column the day someone reorders, adds, or drops a column. Always name the columns — the two extra keystrokes are cheap insurance against a schema change nobody told you about.

### `SELECT INTO` vs `INSERT INTO ... SELECT`

| | `SELECT ... INTO NewTable` | `INSERT INTO ExistingTable SELECT ...` |
|---|---|---|
| Target table | Created by the statement | Must already exist |
| Constraints/indexes copied | **None** — bare columns only | Whatever the target already enforces |
| Identity property copied | Yes (values, not the property itself, unless `IDENTITY()` function used) | Governed by target's own `IDENTITY` |
| Logging | Minimal under simple/bulk-logged recovery | Normal (row-by-row) unless minimal logging conditions are met |
| Typical use | One-off snapshot / staging table | Populating a real, constrained table |

```sql
-- Quick unconstrained snapshot for analysis -- not a substitute for a real table.
SELECT t.* INTO #TaskSnapshot FROM app.Tasks AS t WHERE t.ProjectId = 1;
```

### Bulk loading

| Tool | Where it runs | Typical use |
|---|---|---|
| `INSERT ... VALUES` (multi-row) | T-SQL | Hundreds of rows, hand-authored |
| `BULK INSERT` | T-SQL, server reads the file | CSV/flat file already on the server or a share |
| `bcp` | Command line | Fastest file-based bulk load; scriptable in CI/CD |
| `OPENROWSET(BULK ...)` | T-SQL, inline in a query | Read a file's rows directly into a `SELECT`/`INSERT` without a separate load step |

```sql
-- OPENROWSET(BULK): read a flat file as if it were a derived table.
INSERT INTO app.TimeEntries (TaskId, UserId, WorkDate, Hours)
SELECT TaskId, UserId, WorkDate, Hours
FROM OPENROWSET(BULK 'C:\imports\time-entries.csv', SINGLE_CLOB) AS x; -- illustrative; real usage needs a format file
```

### Identity behaviour

| Function | Scope | Returns |
|---|---|---|
| `SCOPE_IDENTITY()` | Current session, current scope (stored proc/batch) | The last identity **your statement** generated — safe against concurrent inserts and against trigger-inserted rows in other tables |
| `@@IDENTITY` | Current session, any scope | The last identity generated **anywhere** in the session, including inside a trigger — a well-known correctness trap |
| `IDENT_CURRENT('table')` | Any session | The last identity generated **for that table**, by anyone — race-condition-prone under concurrency |

```sql
INSERT INTO app.Labels (LabelName) VALUES (N'flaky-test');
SELECT SCOPE_IDENTITY() AS NewLabelId;    -- the correct choice, almost always
```

> **Rule of thumb:** Use `SCOPE_IDENTITY()`. Reach for `@@IDENTITY` only if you specifically want an identity generated by a trigger on a different table — a design smell in its own right.

`SET IDENTITY_INSERT app.Tasks ON` (as the seed script uses) allows explicit values into an identity column — for exactly one table at a time, and only while the session holds it on. Identity gaps (after a rolled-back transaction, a failed constraint check, or a server restart) are **normal**, not a bug — never write logic that assumes identities are contiguous.

## 2. `UPDATE`

```sql
-- Basic: one table, one predicate.
UPDATE app.Tasks
SET StatusId = 6, CompletedAtUtc = SYSUTCDATETIME()
WHERE TaskId = 5;
```

### `UPDATE ... FROM` and its multi-match trap

T-SQL's `UPDATE ... FROM` extension lets you update one table using values joined from another — but if the join produces **more than one matching row** per target row, the row actually applied is officially **undefined** (SQL Server picks one arbitrarily and does not document which).

```sql
-- DANGEROUS if a task has more than one row in TaskAssignments marked IsPrimary = 1
-- (a data quality bug the schema does not prevent) -- which assignment "wins" is undefined.
UPDATE t
SET t.Title = t.Title + N' (Primary: ' + u.FullName + N')'
FROM app.Tasks AS t
JOIN app.TaskAssignments AS ta ON ta.TaskId = t.TaskId AND ta.IsPrimary = 1
JOIN app.Users AS u ON u.UserId = ta.UserId;
```

Portable, deterministic alternatives:

```sql
-- (1) Correlated subquery -- guaranteed one value, or an explicit Msg 512 if that guarantee breaks.
UPDATE app.Tasks
SET Title = Title + N' (Primary: ' +
    (SELECT u.FullName FROM app.TaskAssignments AS ta
     JOIN app.Users AS u ON u.UserId = ta.UserId
     WHERE ta.TaskId = app.Tasks.TaskId AND ta.IsPrimary = 1) + N')'
WHERE EXISTS (SELECT 1 FROM app.TaskAssignments AS ta WHERE ta.TaskId = app.Tasks.TaskId AND ta.IsPrimary = 1);

-- (2) MERGE -- also deterministic, and reports "more than one match" if you add a constraint.
```

> **Anti-pattern:** `UPDATE ... FROM` against a join whose uniqueness you have not verified. It works fine in testing (where duplicates happen not to exist yet) and corrupts data silently in production the day they do.

### Updating with `TOP` for batching

```sql
-- Update at most 500 rows per iteration -- see §9 for why this matters at scale.
UPDATE TOP (500) app.Tasks
SET StatusId = 7
WHERE StatusId = 1 AND CreatedAtUtc < DATEADD(YEAR, -2, SYSUTCDATETIME());
```

`UPDATE TOP (n)` without an `ORDER BY` picks an arbitrary `n` rows — acceptable for a batching loop that repeats until zero rows are affected, wrong if you need a *specific* n rows (there is no `ORDER BY` support inside `UPDATE`/`DELETE` `TOP` — for a deterministic subset, filter by a subquery that itself uses `TOP ... ORDER BY`).

## 3. `DELETE`

```sql
-- With a join (T-SQL extension, same multi-match caveat as UPDATE ... FROM, but
-- DELETE only removes rows -- there's no "wrong value written," so the risk is lower,
-- though multiple joined rows can still delete more target rows than intended.)
DELETE t
FROM app.Tasks AS t
JOIN app.Projects AS p ON p.ProjectId = t.ProjectId
WHERE p.IsArchived = 1 AND t.StatusId = 7;
```

### `DELETE TOP (n)` batching loop

The standard pattern for purging a large table without one giant transaction and a long-held lock escalation:

```sql
SET NOCOUNT ON;
WHILE 1 = 1
BEGIN
    DELETE TOP (1000) FROM audit.TaskHistory
    WHERE ChangedAtUtc < DATEADD(YEAR, -2, SYSUTCDATETIME());

    IF @@ROWCOUNT = 0 BREAK;

    -- Optional: brief pause so the log can be backed up/truncated between batches
    -- and other sessions get a chance to acquire locks.
    WAITFOR DELAY '00:00:00.100';
END;
```

### `DELETE` vs `TRUNCATE TABLE` vs `DROP TABLE`

| | `DELETE` | `TRUNCATE TABLE` | `DROP TABLE` |
|---|---|---|---|
| Removes | Rows matching `WHERE` (or all, if omitted) | **All** rows, unconditionally | The table itself |
| Logging | Fully logged, row-by-row | Minimally logged (page deallocations) | Minimally logged |
| Speed on large tables | Slow | **Fast** | Fast |
| Fires triggers | Yes | **No** | n/a |
| Resets `IDENTITY` seed | No | **Yes**, back to the seed value | n/a |
| Requires | `DELETE` permission | `ALTER` permission on the table | `ALTER`/ownership |
| Blocked by | Any `FOREIGN KEY` referencing it (row-level check) | **Any** `FOREIGN KEY` referencing the table, even with zero child rows | Any dependent object |
| Rollback | Yes, inside a transaction | Yes, inside a transaction (commonly misunderstood as not) | Yes, inside a transaction |
| `WHERE` clause | Yes | **No** | n/a |

> **Rule of thumb:** `TRUNCATE` is not "a faster `DELETE`, use it anywhere" — it cannot take a `WHERE`, it is blocked outright by any FK reference (§ referential actions, Topic 11), and while it *is* transactional and rollback-capable, teams often deploy it assuming otherwise. Reserve it for full-table resets of staging/import tables.

## 4. The `OUTPUT` Clause

Every DML statement can return the rows it affected, via the `INSERTED`/`DELETED` pseudo-tables — the same two tables triggers use (Topic 16).

| Statement | `INSERTED` has | `DELETED` has |
|---|---|---|
| `INSERT` | The new row(s) | n/a |
| `DELETE` | n/a | The removed row(s) |
| `UPDATE` | The new values | The old values |
| `MERGE` | Depends on which action fired | Depends on which action fired |

```sql
-- Capture the generated key(s) from a multi-row insert -- essential when you need the
-- new TaskId back for a subsequent INSERT into TaskAssignments, and SCOPE_IDENTITY()
-- only gives you the LAST one.
DECLARE @NewTasks TABLE (TaskId INT, Title NVARCHAR(200));

INSERT INTO app.Tasks (ProjectId, Title, StatusId, PriorityId, CreatedByUserId)
OUTPUT INSERTED.TaskId, INSERTED.Title INTO @NewTasks (TaskId, Title)
VALUES (1, N'Add OpenTelemetry tracing', 1, 2, 4),
       (1, N'Instrument slow-query logging', 1, 3, 4);

SELECT * FROM @NewTasks;
```

```sql
-- Build an audit trail directly from an UPDATE -- no trigger required.
UPDATE app.Tasks
SET StatusId = 6, CompletedAtUtc = SYSUTCDATETIME()
OUTPUT
    DELETED.TaskId,
    N'StatusId',
    CAST(DELETED.StatusId AS NVARCHAR(400)),
    CAST(INSERTED.StatusId AS NVARCHAR(400))
INTO audit.TaskHistory (TaskId, ColumnName, OldValue, NewValue)
WHERE TaskId = 5;
```

### Composable DML: archive-and-purge in one statement

`OUTPUT` can feed directly into another `INSERT`, so a delete's output becomes the next statement's source — no staging table, no gap where a row exists in neither place:

```sql
INSERT INTO audit.TaskHistory (TaskId, ColumnName, OldValue, NewValue)
SELECT TaskId, N'ARCHIVED', N'active', N'purged'
FROM (
    DELETE FROM app.Tasks
    OUTPUT DELETED.TaskId
    WHERE StatusId = 7 AND CreatedAtUtc < DATEADD(YEAR, -2, SYSUTCDATETIME())
) AS Purged;
```

> **Rule of thumb:** Any time you're tempted to `SELECT` rows into a staging table before deleting them "just in case," check whether `OUTPUT ... INTO` can do both in one atomic statement instead. It removes the window where the two copies can disagree.

## 5. `MERGE`

`MERGE` compares a source to a target and applies inserts, updates, and deletes in one statement — the canonical "upsert."

```sql
MERGE app.Labels AS tgt
USING (VALUES (N'bug', '#D73A4A'), (N'security', '#B60205'), (N'ai-generated', '#6F42C1'))
       AS src (LabelName, ColorHex)
ON tgt.LabelName = src.LabelName
WHEN MATCHED AND tgt.ColorHex <> src.ColorHex THEN
    UPDATE SET tgt.ColorHex = src.ColorHex
WHEN NOT MATCHED BY TARGET THEN
    INSERT (LabelName, ColorHex) VALUES (src.LabelName, src.ColorHex)
WHEN NOT MATCHED BY SOURCE AND tgt.LabelName = N'wont-fix' THEN
    DELETE
OUTPUT $action, INSERTED.LabelId, INSERTED.LabelName, DELETED.LabelName;
```

`$action` in the `OUTPUT` clause reports which branch fired per row (`'INSERT'`, `'UPDATE'`, or `'DELETE'`) — essential for logging exactly what a `MERGE` did.

### Why many experienced teams avoid `MERGE`

| Concern | Detail |
|---|---|
| **Known correctness bugs** | Microsoft has documented and fixed multiple `MERGE` correctness bugs over the years (e.g. incorrect results with certain trigger/constraint combinations). New teams are often unaware they need to check for these on older SQL Server versions. |
| **Concurrency requires extra locking hints** | Under the default isolation level, two concurrent `MERGE` statements can both see "not matched" for the same key and both attempt an insert, raising a primary-key violation instead of behaving like an atomic upsert. The documented fix is `WITH (HOLDLOCK)` on the target, which most examples online omit. |
| **Halloween-protection overhead** | `MERGE` can require an internal spool to prevent a row from being processed more than once as it moves between the "matched" and "not matched" logical states, adding plan complexity. |
| **Trigger firing surprises** | A single `MERGE` can fire `INSERT`, `UPDATE`, and `DELETE` triggers all in the same statement — easy to forget when writing a trigger that assumes it only ever fires from a plain `INSERT`. |
| **Readability** | Three `WHEN` clauses with independent conditions are harder to review at a glance than two separate, explicit statements. |

### The safer alternative under an explicit transaction

```sql
BEGIN TRANSACTION;

UPDATE tgt
SET tgt.ColorHex = src.ColorHex
FROM app.Labels AS tgt
JOIN (VALUES (N'bug', '#D73A4A'), (N'security', '#B60205')) AS src (LabelName, ColorHex)
    ON tgt.LabelName = src.LabelName
WHERE tgt.ColorHex <> src.ColorHex;

INSERT INTO app.Labels (LabelName, ColorHex)
SELECT src.LabelName, src.ColorHex
FROM (VALUES (N'bug', '#D73A4A'), (N'security', '#B60205'), (N'ai-generated', '#6F42C1'))
        AS src (LabelName, ColorHex)
WHERE NOT EXISTS (SELECT 1 FROM app.Labels AS tgt WHERE tgt.LabelName = src.LabelName);

COMMIT TRANSACTION;
```

Two ordinary statements, in an explicit transaction, are easier to reason about, easier to unit test independently, and carry none of `MERGE`'s documented correctness caveats.

### Upsert race conditions and `WITH (UPDLOCK, HOLDLOCK)`

The `UPDATE`-then-`INSERT` pattern above has its own race: two concurrent sessions can both run the `UPDATE` (0 rows affected, no match yet), both conclude "not matched," and both attempt the `INSERT` — one wins, one hits `UQ_Labels_Name`.

```sql
BEGIN TRANSACTION;

IF NOT EXISTS (
    SELECT 1 FROM app.Labels WITH (UPDLOCK, HOLDLOCK) WHERE LabelName = N'ai-generated'
)
    INSERT INTO app.Labels (LabelName, ColorHex) VALUES (N'ai-generated', '#6F42C1');

COMMIT TRANSACTION;
```

`UPDLOCK` takes an update lock on the row/range as soon as it is read, preventing a second session from doing the same read-then-decide until the first transaction commits. `HOLDLOCK` (equivalent to `SERIALIZABLE` for this statement) extends that lock to cover the *absence* of a row, not just an existing one — without it, a gap in the key range is not protected and two sessions can still both "not find" the row and both insert.

> **Rule of thumb:** Any upsert under real concurrency needs either `MERGE` with `WITH (HOLDLOCK)` on the target, or a manual check guarded by `WITH (UPDLOCK, HOLDLOCK)`. A bare "check then insert" with no locking hint is a race condition waiting for enough traffic to expose it.

## 6. Set-Based vs Row-by-Row (RBAR) Thinking

SQL is set-based by design. Cursors process one row at a time and are almost always the wrong default.

```sql
-- RBAR anti-pattern: one round trip per row, ~35 iterations.
DECLARE @TaskId INT;
DECLARE cur CURSOR FOR SELECT TaskId FROM app.Tasks WHERE PriorityId = 1;
OPEN cur;
FETCH NEXT FROM cur INTO @TaskId;
WHILE @@FETCH_STATUS = 0
BEGIN
    UPDATE app.Tasks SET PriorityId = 2 WHERE TaskId = @TaskId;
    FETCH NEXT FROM cur INTO @TaskId;
END;
CLOSE cur; DEALLOCATE cur;

-- Set-based: one statement, one plan, done.
UPDATE app.Tasks SET PriorityId = 2 WHERE PriorityId = 1;
```

The set-based version is not just shorter — it lets the optimizer choose a single efficient plan instead of paying per-row overhead (parsing, locking, logging) 35 separate times. Legitimate cursor use is rare: genuinely sequential administrative scripts (looping over database names, calling a system procedure per database) are one of the few defensible cases.

## 7. Constraints, Triggers, and DML Ordering

For a single DML statement, SQL Server evaluates in roughly this order: `INSTEAD OF` triggers (if any) → constraints (`DEFAULT`, `NOT NULL`, `CHECK`, `FOREIGN KEY`, `UNIQUE`/`PRIMARY KEY`) → the actual data modification → `AFTER` triggers. A constraint violation anywhere rolls back the entire statement — including every row an `INSERT ... SELECT` would otherwise have added, not just the offending row.

```sql
-- If even one row violates CK_TimeEntries_Hours, NONE of the 50 rows are inserted.
INSERT INTO app.TimeEntries (TaskId, UserId, WorkDate, Hours)
SELECT TaskId, UserId, WorkDate, Hours FROM #StagingTimeEntries;
```

## 8. Safety Checklist for Ad-Hoc DML

1. **Write the `SELECT` first.** Turn `UPDATE t SET ... WHERE ...` into `SELECT * FROM t WHERE ...` and eyeball the row count before changing a single keyword.
2. **Wrap it in an explicit transaction** when running ad hoc: `BEGIN TRANSACTION; <statement>; -- inspect @@ROWCOUNT and OUTPUT --  COMMIT;` (or `ROLLBACK` if the row count surprises you).
3. **`SET XACT_ABORT ON`** at the top of any script with multiple statements in a transaction, so a runtime error automatically rolls back the whole batch instead of leaving it half-applied.
4. **Check `@@ROWCOUNT`** immediately after the statement — a silent 0-row or 35,000-row `UPDATE` are both signs something is wrong with the predicate.
5. **Never trust a `WHERE`-less `UPDATE`/`DELETE`** you didn't write yourself. Read the whole statement before running it, every time.
6. **Batch large operations** (§2, §3) rather than one multi-million-row transaction, to bound log growth and avoid lock escalation.

```sql
SET XACT_ABORT ON;
BEGIN TRANSACTION;

    UPDATE app.Tasks SET PriorityId = 2 WHERE PriorityId = 1;
    PRINT CONCAT('Rows affected: ', @@ROWCOUNT);

    -- Eyeball the count. If it looks right:
COMMIT TRANSACTION;
    -- If it looks wrong, run ROLLBACK TRANSACTION; instead.
```

## 9. Batching Strategy for Large DML

| Concern | Why batching helps |
|---|---|
| **Transaction log growth** | One giant transaction keeps every log record active until commit; batches let the log truncate (under simple recovery) or ship (under full recovery with log backups) between iterations |
| **Lock escalation** | SQL Server escalates row/page locks to a table lock around ~5 000 locks in a single statement by default, blocking all other readers/writers; smaller batches stay under that threshold |
| **Blocking duration** | A multi-million-row `DELETE` can hold locks for minutes; a 1 000-row batch loop yields regularly, letting other sessions interleave |
| **Resumability** | If a batch loop fails or is cancelled partway, the work already committed stays done; a single giant transaction rolls all the way back to nothing |

A chunk size of 1 000–5 000 rows per batch is a reasonable starting point; tune based on observed lock waits and log growth in your environment.

## Mental Model

> `INSERT`, `UPDATE`, and `DELETE` are the only statements that change what the database believes is true, and every one of them runs inside the same transaction as the constraints that guard it — which is exactly why "always list your `INSERT` columns" and "always `SELECT` before you `UPDATE`/`DELETE`" are not paranoia, they are the two habits that catch a schema drift or a wrong predicate before it commits. `OUTPUT` turns any DML statement into its own audit trail via the `INSERTED`/`DELETED` pseudo-tables, and can feed directly into another table in the same statement — the composable archive-and-purge pattern — so you never have a window where a row exists in neither the old place nor the new. `MERGE` looks like the elegant single-statement upsert, but it carries real, documented correctness and concurrency caveats that two explicit statements under `WITH (UPDLOCK, HOLDLOCK)` do not; prefer the boring version unless you have specifically read and mitigated `MERGE`'s known issues. And at scale, the discipline shifts from correctness to blast radius: batch large operations in the thousands of rows, not millions, because the failure mode of one giant DML transaction is not "it's slow" — it's a table lock that stops every other session in the system until it finishes or rolls all the way back.
